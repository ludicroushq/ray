# Project Instructions

- Do not run dev servers or database-altering CLIs without explicit user permission. Complete static work first, then tell the user which interactive commands remain.
- Treat `.ruler` as the source of truth for agent instructions and skills. Do not edit generated `AGENTS.md`, `CLAUDE.md`, `.agents/skills`, `.claude/skills`, or `.cursor/skills`; run `bun ruler` after source changes and `bun run skills:update` to update lockfile-managed external skills.
- Treat this repository as a reusable app starter for complex applications. Keep applications unscoped, reserve `@repo/*` for internal packages, and put shared app and environment configuration in `@repo/config`. Read `docs/effect-confect.md` before adding application services or backend functions.
- Author backend functions, schemas, and auth configuration in `packages/backend/confect`. Confect generates the adapters in `packages/backend/convex`; keep native `convex.config.ts` and `tsconfig.json` there. Use native Convex APIs for crons/component configuration and Confect's plain Convex function support for unsupported capabilities. Do not hand-edit generated files or put authored helpers/tests in `convex`, where codegen can delete them. Confect is community-maintained; upgrade its pinned version together with Effect and rerun generation, types, and focused tests.
- Run local Confect generation with `bun run confect:codegen` before typechecking or deploying changed backend contracts. Run native Convex CLI commands from the root with `bun convex`; the backend's `dev` script generates adapters first, then runs `confect dev` and `convex dev` together. Confect's watcher alone does not synchronize a Convex deployment. The backend owns `convex.json`; the root owns shared environment configuration. Read `packages/backend/convex/_generated/ai/guidelines.md` before changing backend code, using the Confect conventions here for function authoring.
- Use Effect for nontrivial application services and external integrations. Keep framework handlers and React components idiomatic. Model expected failures with tagged errors and inject service dependencies; provide services and deliberately handle expected errors before calling `runEffect` from `@repo/effect/runtime`. Do not use `orDie`, broad catch-all recovery, casts, or lint suppressions merely to empty the error/dependency channel. Defects remain failures. Confect owns execution of backend handlers; do not create runtimes or run Effects inside them.
- Use Effect Schema for new domain contracts and Confect function/table schemas. Keep the existing Zod environment and FormAdapter contracts; do not duplicate schemas or introduce a custom schema converter. Add explicit adapters only where an integration needs a different wire format.
- For WorkOS AuthKit, keep sign-in and sign-up distinct, redirect login to `/app`, and use the canonical `appUrl` as the logout return target. Use the public portless URL for local callbacks and the SDK's standard server environment variables. Use the client `signOut()` flow for browser-initiated logout.
- Put values shared by browser and server code in `@repo/config/env/client` with a `VITE_` name. Use the canonical `appUrl` unless the browser genuinely needs a runtime environment value.
- In a custom TanStack Start `src/start.ts`, keep same-origin CSRF validation before authentication middleware. Do not set the router's global `defaultPendingMs` to `0`, which can replace server-rendered HTML during hydration.
- Use `convex-route-query` for Convex route loaders and React queries. Use typed native references from `@repo/backend/native`, derived from generated Convex adapters; they expose encoded wire values and native Convex errors. Use `@repo/backend/refs` with Confect-aware callers when decoded values/errors are required. Bare Confect 9 `Ref.getFunctionReference` drops argument/result types. Do not add a second subscription/cache for the same function. Do not enable global `expectAuth` while public routes can subscribe logged out; enforce private access in protected layouts and backend functions.
- Use PostHog SDKs directly and keep their established environment variable names. Send Convex logs and errors through dashboard integrations; use `@posthog/convex` for backend events and flags, and keep build credentials separate from runtime project tokens.
- Keep Migrations and Workflow registered as starter defaults. Workpool is Workflow's peer and should only be mounted separately for an independent pool; add other Convex components only for concrete product needs.
- Treat TanStack Start as the public HTTP and integration boundary. Implement webhooks, callbacks, and custom API endpoints as TanStack Start server routes; validate and authenticate requests there, then use Convex for durable data changes and background work. Do not add Convex HTTP actions unless a concrete platform constraint requires one.
- Let browser code call Convex directly for application queries and routine authenticated mutations, including CRUD operations and form submissions. Do not proxy these operations through TanStack Start.
- Keep durable state, authorization enforcement, business mutations, scheduled work, and background jobs in Convex. Use Confect spec/implementation pairs and `withAuthenticatedIdentity` for authenticated handlers; derive identity from the request and enforce ownership/organization access in each operation. Declare only sanitized, serializable public error schemas. Use `tokenIdentifier` as the canonical identity key for authorization and stored records. Keep database writes in mutations and external side effects in actions. Use Convex Workflow/scheduling for durable work; Effect fibers, retries, and scopes do not survive a terminated request. Do not retry non-idempotent external writes or add network/timer work to deterministic queries/mutations.
- Use FormAdapter for straightforward web forms. Keep `DaisyUIProvider` at the app root, create provider-neutral forms from `@formadapter/react`, submit to Convex through ordinary `onSubmit` handlers, and add `@formadapter/tanstack-start` only for TanStack Start server functions.
- Keep at least one representative starter test, with component tests under `__tests__`. Do not invent backend behavior solely for a sample test.
